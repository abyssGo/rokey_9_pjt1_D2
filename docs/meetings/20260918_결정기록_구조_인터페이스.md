# 구조 변경 결정 (DSN-02b · 9/18 저녁)

## 왜 바꾸는가
두산 파이썬 API(`DSR_ROBOT2`)는 **혼자 위에서 아래로 도는 스크립트**를 전제로 만들어졌다. 로봇 명령마다 자기가 실행기를 돌려 응답을 기다린다. 서비스 콜백 안에서 쓰면 교착하고(TS-01 B), 우회해도 "두 번째 호출부터 멈춤"(TS-01 B′), 프로세스를 나누면 "겹친 명령을 조용히 덮어씀"(TS-01 증상 C) 같은 함정이 남는다. 코드가 아직 없는 지금 구조를 바꾸는 것이 가장 싸다.

## 비교한 구조 (9/18 저녁, Virtual + 실제 `dsr_controller2`)
| 구조 | 결과 | 판단 |
|---|---|---|
| ① 기능 노드 3개(프로세스 3개) + 각자 DSR 전용 노드 | 번갈아 9회·연속 3회 성공. **다른 프로세스의 명령이 겹치면 드라이버가 덮어쓰고 양쪽 다 성공 응답** | 위험 남음 |
| ② 로봇 서버 노드 1개(기능 노드는 클라이언트) | 9/19 시험: 번갈아 9회 성공, 겹친 요청은 `BUSY`. 단 기능 노드를 기본 `rclpy.spin`으로 만들면 콜백 안 동기 호출에서 교착 | 동작은 하지만 서버 인터페이스(서비스 열몇 개) 신설·힘제어 루프가 서비스를 건넘·중첩 호출 규약 필요 → 이 일정에서는 작업량 큼 |
| ③ 한 프로세스에 기능 노드 3개 + DSR 전용 노드 공유 | 번갈아 9회 성공, 겹친 요청은 `BUSY` 거절 | 절충안 |
| **④ 스크립트형: 기능은 함수, 메인 스레드가 차례로 실행, 통신 노드만 백그라운드** | **연속 6회 성공, 모션 중 상태 2.000 Hz, stop 수락** | **채택** |
| 두산의 클래스 API(`CDsrRobot`) | 같은 대기 방식 + 우리 설치본은 서비스 이름이 달라 스크립트에서도 무한 대기 | 해당 없음 |

④를 고른 이유: 문제가 생길 자리가 없다(두산이 의도한 사용법) · 강사 배포 예제 5개가 모두 이 방식 · 검증된 코드의 비율이 가장 높다 · 우리 시연에 필요한 것(시나리오·HMI·기록·역할 분담)을 잃지 않는다.

## 이전 프로젝트(IDC 순찰로봇)와 같은 원칙
로봇에게 명령하는 노드는 하나(`mission_manager` ↔ `flow_node`), 미션의 단계는 그 안의 상태 머신(UNDOCK·NAVIGATE·INSPECT ↔ pick·weigh·wipe·rack), 실제로 움직이는 서버는 제조사 제공(Nav2·Create3 ↔ `dsr_controller2`·그리퍼 드라이버). 이전 프로젝트의 기능별 노드(YOLO·ArUco·Event_engine)는 **감지·판정** 노드였고 로봇에게 명령하지 않았다 — 이번에는 비전이 없어 그 층이 없다. 두산 드라이버는 Nav2와 달리 동기 서비스(취소·피드백 없음, 겹치면 덮어씀)라 명령 경로를 하나로 모아야 안전하다.
